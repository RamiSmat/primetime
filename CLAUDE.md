# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

PrimeTime is an early-stage open-source utility that schedules lightweight "primer" requests for AI coding tool CLIs (Claude Code, OpenAI Codex, Google Antigravity), so a provider's usage window starts before the user's normal coding session begins.

The intended end-to-end architecture is:

```
User → PrimeTime web UI → GitHub account / private PrimeTime repo → GitHub Actions → AI provider CLI
```

Provider credentials must always live in infrastructure the user controls (e.g. GitHub Actions secrets). **PrimeTime's backend must never receive, store, or log provider authentication material** (passwords, cookies, session tokens, API keys). This is an architectural constraint, not a style preference — see `AGENTS.md` for the full list of security invariants before touching anything related to auth, credential storage, or GitHub Actions workflow generation.

Currently implemented: a `primetime prime <provider>` CLI backed by a real Codex adapter that runs one minimal, sandboxed `codex exec` request through the official Codex CLI, and a real Claude Code adapter that runs one minimal, sandboxed `claude -p` request through the official Claude Code CLI (see the Codex and Claude Code provider sections in the README for the exact safety flags and failure classification). `primetime setup <provider>` (e.g. `setup codex`) transfers your local Codex session (`$CODEX_HOME/auth.json`) directly to the current repository's `CODEX_AUTH_JSON` GitHub Actions secret via `gh secret set` (see `@primetime/github`) — it does not authenticate Codex itself; run `codex login` locally first. `setup claude-code` is the Claude Code equivalent, but reads a token from **stdin** instead of a local file, since `claude setup-token` prints a one-year long-lived `CLAUDE_CODE_OAUTH_TOKEN` to the terminal and never writes it to disk (unlike Codex's `auth.json`, this token also needs no refresh/write-back step): run `claude setup-token` locally first, then `echo "$THE_TOKEN" | primetime setup claude-code`. `primetime setup github-secrets-pat` (PAT value read from stdin) stores the `PRIMETIME_SECRETS_PAT` secret a scheduled workflow needs to write a refreshed session back, since GitHub's default `GITHUB_TOKEN` can't manage secrets and there's no API to mint a PAT programmatically. `primetime schedule next <config-path> <provider>` reads a schedule config file and prints the next primer run for that provider (looking up its `usageWindowMinutes` — see `@primetime/providers#ProviderAdapter` — to compute it), computed by the timezone/DST-aware `@primetime/scheduler` package — it only reports that time, it doesn't trigger anything. `templates/github-actions/codex-prime.yml` is the actual scheduled workflow tying `prime`/`setup` together (bootstrap `auth.json` from the secret → run `prime` → write the refreshed `auth.json` back via `setup codex` again, from inside the runner). It's provisional: PrimeTime isn't published as an installable package yet, so the workflow checks out and builds this repo's own source on the runner. `packages/github-app` (GitHub App JWT signing, installation-token minting, Actions-OIDC verification, webhook signature checking) and `apps/web` (a Next.js backend exposing `/api/github/webhook` and `/api/actions/token`) implement an optional hosted alternative to the PAT write-back step — see the README's "Hosted setup (GitHub App)" section — that still never lets the Codex session touch PrimeTime's backend. `templates/github-actions/codex-prime-hosted.yml` is the matching workflow variant. `apps/web` also now serves the actual web UI: a doc-style landing page, "Sign in with GitHub" (GitHub App user-to-server OAuth, session in a signed `pt_session` cookie — GitHub identity for the UI itself, never a provider credential), and `/dashboard`. The dashboard does not let a user browse or pick from their existing repositories — the architecture is built around one dedicated "private PrimeTime repo" per user — so it has a single "Create my warmup repository" button that creates a private `primetime-warmup` repository via one round trip through GitHub's OAuth screen (prompting an install first only the one time an account doesn't have the App yet), then shows one copy-paste command (repository name and this deployment's URL already filled in) that runs `scripts/setup-warmup-repo.sh` — a plain, reviewable shell script that checks prerequisites, logs the user into `gh`/Codex only if needed, transfers the Codex session to the repo's secret, and adds the scheduled workflow file, announcing each step as it runs.

## Commands

```sh
npm install
npm run typecheck   # tsc -b --pretty false (project references across all packages)
npm run build       # tsc -b
npm test            # builds, then runs node --test against compiled test files
```

Tests are plain `node:test` files compiled to JS; there is no test runner watch mode. To run a single test file after building:

```sh
node --test apps/cli/dist/test/arguments.test.js
```

To exercise the CLI directly after building:

```sh
node apps/cli/dist/src/bin.js prime codex
node apps/cli/dist/src/bin.js prime claude-code
node apps/cli/dist/src/bin.js schedule next ./schedule.json <provider>
node apps/cli/dist/src/bin.js schedule due ./schedule.json <provider> [--tolerance-minutes <n>] [--last-primed-at <iso-timestamp>]
node apps/cli/dist/src/bin.js setup codex
echo "$THE_TOKEN" | node apps/cli/dist/src/bin.js setup claude-code
echo "$YOUR_PAT" | node apps/cli/dist/src/bin.js setup github-secrets-pat
```

There is no lint script configured yet at the root (`apps/web` has its own `next lint`, since it sits outside the `tsc -b` graph — see below).

`apps/web` is a Next.js app and is deliberately **not** part of the root `tsc -b`/`npm test` graph above — Next.js does its own type-checking and bundling. Build `packages/github-app`, `packages/scheduler`, and `packages/shared` first (`npm run build` at the root), then:

```sh
npm run build -w apps/web    # next build
npm test -w apps/web         # tsx --test against every file in apps/web/test
```

## Architecture

This is an npm workspaces monorepo (`apps/*`, `packages/*`) built with TypeScript project references (`tsconfig.json` at the root references each package; each package has its own `tsconfig.json` extending `tsconfig.base.json`) — except `apps/web`, which uses Next.js's own TypeScript setup and is intentionally excluded from the root references graph. `tsconfig.base.json` enables strict mode plus `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` — keep new code compliant rather than relaxing these.

- `apps/cli` — the `primetime` binary. `bin.ts` wires stdout/stderr/stdin into `index.ts#runCli`, which parses args (`arguments.ts`) into a `prime`, `schedule-next`, `schedule-due`, `setup-provider`, or `setup-github-secrets-pat` command. `prime` resolves a provider via `@primetime/providers` and prints the provider's own sanitized `PrimeResult.message`/`ProviderSetupResult.message` on both success and failure (never a raw/generic string, and never raw captured CLI output) — `setup-provider` does the same via `provider.setup()`. `schedule-next <config-path> <provider>` and `schedule-due <config-path> <provider> [--tolerance-minutes <n>] [--last-primed-at <iso-timestamp>]` both resolve `<provider>` via `@primetime/providers#selectProvider` (an unknown provider throws `UnknownProviderError`, same as `prime`/`setup`) and pass its `usageWindowMinutes` into the scheduler call, since different providers can have different usage-window lengths. `schedule-next` reads and validates a JSON config file (`schedule.ts#readScheduleConfigFile`, wrapping file/JSON errors in `ScheduleConfigFileError`) and prints the result of `@primetime/scheduler#computeNextPrimerRun`. `schedule-due` reads the same config and calls `@primetime/scheduler#isPrimerDue` — it's the timezone/DST-aware decision point a scheduled workflow polls on a frequent, fixed cron cadence (see `templates/github-actions` below) instead of trying to compute one precise `cron:` line: exit `0` means a primer is due right now, exit `2` (`SCHEDULE_NOT_DUE_EXIT_CODE`, exported from `index.ts`) means it isn't (an expected outcome, printed to stdout, never `writeError`), and exit `1` is a real error (bad path/JSON/config), same as every other command. `--last-primed-at`, when given, lets `isPrimerDue` catch up on an instant that's already passed the tolerance window as long as no primer has succeeded since — see `packages/scheduler` below for why a fixed tolerance alone isn't enough for a real-world scheduler. `setup-github-secrets-pat` (`github-secrets-pat.ts`) reads a PAT from `io.readInput()` (real stdin in `bin.ts`, a fake in tests — secret values must never be CLI args) and stores it as `PRIMETIME_SECRETS_PAT` via `@primetime/github`, which it takes an injectable `GhRunner` for, same DI pattern as `CodexProvider`.
- `packages/providers` — the `ProviderAdapter` interface (`adapter.ts`: `detect`/`setup`/`validateAuthentication`/`prime`, plus `usageWindowMinutes` — how long that provider's subscription usage window stays warm after a primer, consumed by `@primetime/scheduler`'s rolling-window scheduling — and the structured `PrimeResult` and `ProviderSetupResult`, each carrying a sanitized `message`) and the provider registry (`registry.ts`, a lookup map keyed by lowercased provider id). Each provider lives in its own subdirectory and is added to the `providers` map in `registry.ts`. `UnknownProviderError` deliberately does not echo the invalid input back in its message (tested in `apps/cli/test/providers.test.ts`) — preserve that when editing.
  - `codex/` — the real Codex adapter: `index.ts`'s `CODEX_USAGE_WINDOW_MINUTES` is a hardcoded, doc-commented assumption (currently 5h) for `usageWindowMinutes` — verify against OpenAI's current docs before relying on it, it isn't sourced from any API. `process-runner.ts` is an injectable, `cross-spawn`-based subprocess runner (constructor-injected into `CodexProvider`, defaulting to the real one — tests inject a fake runner instead of invoking the real CLI); `classification.ts` classifies `codex login status` / `codex exec` outcomes from **combined stdout+stderr** (the installed CLI writes some status text to stderr, not stdout — don't assume otherwise); `messages.ts` maps every failure to a fixed, sanitized string, never built from captured output; `command.ts`/`environment.ts`/`workspace.ts` build the exact `codex exec` safety flags, strip `OPENAI_API_KEY`/`CODEX_API_KEY` from the child env, and run each primer request inside a freshly created, always-deleted temp directory; `auth-file.ts` reads `$CODEX_HOME/auth.json` (never logs or includes its contents in any message) for `setup()`, which hands it to `@primetime/github#setRepositorySecret` — `CodexProvider`'s second constructor param is an injectable `GhRunner`, mirroring the codex `SubprocessRunner` pattern, so tests never invoke the real `gh` CLI.
  - `claude-code/` — the real Claude Code adapter (`index.ts`'s `CLAUDE_CODE_USAGE_WINDOW_MINUTES` is the same kind of hardcoded, doc-commented `usageWindowMinutes` assumption as Codex's, currently also 5h — verify against Anthropic's current docs), mirroring `codex/`'s file breakdown but reusing `codex/process-runner.ts`'s `SubprocessRunner` directly (it's fully generic) rather than duplicating it: `classification.ts` classifies `claude auth status` / `claude -p ... --output-format json` outcomes by **parsing structured JSON** (`{loggedIn, authMethod, apiProvider, apiKeySource}` for auth status; `{is_error, api_error_status, result}` for a primer result) rather than regex-matching text — verified live against the installed CLI (`claude` 2.1.278), including that an `apiKeySource` field means an API key would be used and must be rejected; `messages.ts` mirrors `codex/messages.ts`'s fixed-literal-only rule; `command.ts`/`environment.ts`/`workspace.ts` build the exact `claude -p` safety flags (no working-directory flag exists on `claude`, unlike Codex's `-C`, so the ephemeral workspace is applied via the subprocess's own `cwd` only), strip `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` from the child env, and run each primer request inside a freshly created, always-deleted temp directory. `oauth-token.ts` is the one structural difference from Codex: `claude setup-token` generates a one-year `CLAUDE_CODE_OAUTH_TOKEN` but **never writes it to disk** (unlike Codex's `auth.json`), so `setup()` reads it from **stdin** via a constructor-injected `readInput` function (third constructor param, defaulting to real `process.stdin`, same DI pattern as `SubprocessRunner`/`GhRunner`) instead of a file, and validates that the pasted token actually authenticates before it is ever written to the repository's secret.
- `packages/github` — a thin wrapper around the `gh` CLI (own `cross-spawn`-based `GhRunner`, same injectable-for-tests pattern as the codex provider). `resolveRepository` shells out to `gh repo view --json nameWithOwner` rather than parsing git remotes itself; `setRepositorySecret` shells out to `gh secret set`, piping the value over **stdin** (never as a CLI arg, never via env) so it can't leak through process listings, and never implements its own encryption — `gh` performs GitHub's required sealed-box encryption locally before anything leaves the machine. Distinct from `packages/github-app` below: this one shells out to the local `gh` binary on the end user's machine (used by `CodexProvider.setup()`); that one talks to GitHub's HTTPS API as the GitHub App itself, for the hosted backend.
- `packages/github-app` — server-side GitHub App logic for the hosted backend, no overlap with `packages/github`. `app-jwt.ts#signAppJwt` signs the App's own short-lived JWT (RS256 via `jose`, `iat`/`exp` within GitHub's required bounds) used only to authenticate as the App before minting tokens. `installation-token.ts#mintInstallationToken` calls `POST /app/installations/{id}/access_tokens` to mint a token scoped to exactly one `repository` and exactly the `permissions` passed in, via an injectable `fetchImpl` (same DI pattern as `GhRunner`/`SubprocessRunner` — defaults to global `fetch`, tests never hit the network). `oidc.ts#verifyActionsOidcToken` fetches GitHub Actions' published JWKS and verifies a runner's OIDC token's signature/issuer/audience/expiry via `jose`, returning its claims (notably `repository`) — this is the sole trust boundary the token-exchange endpoint relies on. `webhook.ts#verifyWebhookSignature` does a timing-safe HMAC-SHA256 check of `X-Hub-Signature-256` against the raw (unparsed) request body. All errors reuse `@primetime/shared`'s `PrimeTimeError`/`FailureKind` and never include the private key or a raw token value in a message (tested).
- `packages/scheduler` — computes primer run times from a `ScheduleConfig` (timezone, work-start time, lead time, active weekdays, and `deadTimeWindows` — recurring daily `{startTime, endTime}` gaps like lunch or meetings, defaulting to `[]` so every pre-existing config/behavior is unchanged) plus a caller-supplied `usageWindowMinutes` (how long a provider's usage window stays warm after a primer — see `ProviderAdapter.usageWindowMinutes` in `packages/providers`; kept out of `ScheduleConfig` itself and threaded in as a plain parameter so this package stays provider-agnostic, never importing `@primetime/providers`). `timezone.ts` does all local-time/UTC/DST conversion using only the native `Intl` API (no date library dependency); `config.ts#parseScheduleConfig` validates untrusted input, including `parseDeadTimeWindow` (rejects a malformed/reversed/zero-length window) and a check that windows don't overlap. `schedule.ts#computePrimerInstantsForDate` computes every primer instant for one local calendar date by building the day's active intervals (workStart-to-dayEnd with each dead-time window carved out) and, per interval, firing an instant `leadTimeMinutes` before it starts — clamped to never precede whichever dead-time window immediately preceded that interval, which is what fixes a `leadTimeMinutes` longer than a short dead-time window from producing an instant before the window even begins — plus additional `"rolling-refresh"` instants spaced `usageWindowMinutes - leadTimeMinutes` apart for any interval longer than the usage window, so a long active stretch stays continuously warm rather than getting just one instant per day. Throws `LeadTimeExceedsUsageWindowError` if `leadTimeMinutes` isn't strictly less than `usageWindowMinutes`. Both `computeNextPrimerRun` (walks forward day-by-day for the next such instant strictly after `now`) and `isPrimerDue` (checks whether `now` is within a tolerance of any instant on the local calendar day before/on/after `now` — three days, not one, specifically so an instant computed for tomorrow's date that lands just after local midnight today isn't missed) are built on it and take `usageWindowMinutes` as a required parameter. `isPrimerDue` takes an optional fifth `lastPrimedAt?: Date` parameter: when given, an already-past instant is also due as long as `lastPrimedAt` predates it, regardless of how far outside `toleranceMinutes` `now` is — a catch-up for GitHub Actions' `schedule` trigger, which is best-effort and has been observed dropping ticks for hours, not just delaying them by minutes (a fixed symmetric tolerance alone can't absorb an outage of unpredictable length). Omitting it preserves the original tolerance-only behavior exactly. `schedule-due` in `apps/cli` and the GitHub Actions templates below are `isPrimerDue`'s consumers; `apps/web` also depends on this package (for `parseScheduleConfig` client- and server-side in the warmup-settings form/API) even though it never runs a provider adapter.
- `packages/shared` — cross-package primitives, currently just `PrimeTimeError`, a typed error base class keyed by `FailureKind` (`authentication_expired`, `provider_unavailable`, `rate_limited`, `cli_unavailable`, `invalid_configuration`, `network_failure`, `not_implemented`, `unknown_failure`). New error types across the codebase should extend this and pick the closest `FailureKind` rather than inventing ad hoc error shapes.
- `apps/web` — the hosted backend (Next.js App Router, deployed to Vercel; DB is Neon Postgres via Drizzle, `DATABASE_URL`). Route handlers stay thin (validate input, call `packages/github-app` and the DB store, return a `Response`) with the actual logic in plain, DI-friendly functions they wire up: `src/github/webhook-handler.ts#handleGithubWebhook` verifies the webhook signature against the raw body, then on `installation`/`installation_repositories` events updates the `InstallationStore`; `src/actions/token-handler.ts#handleActionsTokenRequest` verifies the caller's bearer OIDC token, looks up an installation for the verified `repository` claim, and — only if one exists — mints and returns a token scoped to just that repository and `{ secrets: "write" }`, rejecting (401/403) otherwise. `app/api/github/webhook/route.ts` and `app/api/actions/token/route.ts` are the actual routes, each just wiring env vars and `src/db/store.ts#getInstallationStore()` into the handler above. `src/db/schema.ts` defines three Drizzle tables: `github_installations` and `installation_repositories` (one-to-many since the `installation_repositories` webhook event changes a repo's coverage independently of the installation record), plus `warmup_settings` (one row per GitHub account, keyed by `account_login`, storing a validated `ScheduleConfig` and a per-provider `subscriptionCounts` map as `jsonb` blobs rather than exploded columns, since `@primetime/scheduler#parseScheduleConfig` is already the one authoritative shape/validator for the former and the latter is inert data — see below). **There is no migration tooling in this repo** (no `drizzle-kit` config, no SQL migration files) — a new table needs a manual DDL step against the Neon database, the same way the first two tables were provisioned. `src/db/store.ts#InstallationStore` is the interface for the first two tables, with `DrizzleInstallationStore` for production and `InMemoryInstallationStore` (a Map-based fake) for tests, so route-handler tests (`apps/web/test/`) never need a real Postgres connection; it also has `listRepositoriesForAccount(accountLogin)`, which the dashboard uses to check whether the signed-in user already has a warmup repository. `src/db/warmup-settings-store.ts#WarmupSettingsStore` (`getSettings`/`saveSettings`, `DrizzleWarmupSettingsStore`/`InMemoryWarmupSettingsStore`, same DI-for-tests pattern) is `warmup_settings`'s equivalent, kept as its own file/interface rather than folded into `InstallationStore` since it's an unrelated concern. `src/settings/warmup-settings-handler.ts#handleGetWarmupSettings`/`handleSaveWarmupSettings` take `user: SessionPayload | undefined` as a parameter (resolved by the route adapter via `getCurrentUser()`, never read internally) so they're testable with a plain `Request` and a fake session/store; saving re-validates the schedule via `parseScheduleConfig` (400 with its message on failure, never a generic string) and checks `subscriptionCounts` values are non-negative integers, never against the provider registry — that data is purely inert, for a future multi-account-credential-storage issue to consume. `app/api/settings/warmup/route.ts` (GET/PUT) is the thin route wiring `getCurrentUser()`/`getWarmupSettingsStore()` into those handlers, mirroring `app/api/actions/token/route.ts`'s pattern. `.env.example` documents required env var *names* only, never values.

The web UI (`app/page.tsx`, `app/dashboard/page.tsx`) is built on top of `src/auth/`: `github-oauth.ts` talks to GitHub's OAuth endpoints directly; `session.ts` signs/verifies a `pt_session` JWT cookie via `jose` and also encodes an `OauthIntent` (`signin`, `provision-repo`, or `install-app`) into the CSRF `state` value so one OAuth round trip can serve "just sign in" as well as "sign in, then create my warmup repo"; `current-user.ts#getCurrentUser` reads the session cookie in server components. `app/api/auth/login/route.ts` accepts `?intent=`; per `OauthIntent`'s doc comment, only `install-app` goes through `src/github/install-url.ts#buildInstallUrl` (the URL that actually installs the App — but which dead-ends at GitHub's own "manage installation" settings page, never redirecting back, for an account that already has it installed), so the dashboard's default "Create my warmup repository" button uses `provision-repo` (the plain authorize URL, which works the same regardless of install state) and only offers an `install-app` link from the `not_installed` error card, for that one first-time case. `app/api/auth/callback/route.ts` decodes the intent and, for either `provision-repo` or `install-app`, uses the just-issued (never persisted) GitHub user access token to call `src/github/user-installations.ts#findUserAppInstallation` (checks `GET /user/installations` directly against GitHub — not the DB — so it's always fresh) and then `src/github/provision-repo.ts#provisionWarmupRepo`. That function does **not** call the GitHub API to create the repository — `POST /user/repos` rejects every kind of GitHub App token (user-to-server included) with `403 Resource not accessible by integration`, confirmed against the real deployment; GitHub reserves account-level repo creation for classic PATs and OAuth Apps, neither of which this project asks users for. It only records the deterministic `<login>/primetime-warmup` name with `store.addRepositories` — the actual `gh repo create` happens inside `scripts/setup-warmup-repo.sh`, using the user's own full-scope local `gh` login, which has no such restriction. This still only works when the installation's `repository_selection` is `"all"` (so that once the script creates the repo, the App's installation actually covers it — GitHub's "add a single repository to an installation" endpoint is separately PAT-only, so there's no other way to extend a `"selected"` installation to a not-yet-existing repo) — a `"selected"` installation surfaces `RepositorySelectionNotAllError` back to the dashboard as an actionable error instead of silently failing. Since "all repositories" access means the installation (and `listRepositoriesForAccount`) covers every repo the account has, not just the one PrimeTime uses, the dashboard picks the one matching `WARMUP_REPO_NAME` rather than taking the first result. None of this is a provider (Codex/Claude/etc.) credential; it's ordinary GitHub identity/authorization for the web UI itself. `app/(site)/dashboard/settings/page.tsx` is the warmup-schedule settings page (linked from the dashboard as "Warmup schedule"): a server component that loads the signed-in account's saved `warmup_settings` row (or `DEFAULT_SCHEDULE_CONFIG`/`DEFAULT_SUBSCRIPTION_COUNTS` if none yet) and renders `components/warmup-settings-form.tsx` (`"use client"`) — time zone, work-start time, lead time, active-weekday toggles, an editable list of dead-time windows, and a subscription-count input per `AVAILABLE_PROVIDERS` entry (recorded as inert data only — see the `apps/web` bullet above). It validates via `@primetime/scheduler#parseScheduleConfig` client-side before `PUT`ting to `/api/settings/warmup`, which re-validates authoritatively. New `components/ui/input.tsx`/`label.tsx` primitives back the form's native `<input type="time"/"number">` fields (`Input`'s cva size variant is named `uiSize`, not `size`, since `size` collides with the native HTML input attribute of the same name). The dashboard's `components/provider-picker.tsx` (`"use client"`) lets the user toggle which provider(s) — `lib/providers.ts#AVAILABLE_PROVIDERS`, currently `codex` and `claude-code`, both selected by default — to warm up, takes the account's current `ScheduleConfig` as a prop (fetched by the dashboard page the same way the settings page does), then recomputes the setup command via `lib/setup-command.ts#setupCommandUnix`/`setupCommandWindows` (pure functions, unit-tested in `apps/web/test/setup-command.test.ts`) and renders it through `components/os-command-tabs.tsx`, which shows a per-OS copy-paste command defaulting to a client-side-detected tab: macOS/Linux runs [`scripts/setup-warmup-repo.sh`](../../scripts/setup-warmup-repo.sh) (`curl -fsSL <raw-url> | bash -s -- <owner>/<repo> <primetime-web-url> [provider...] [--schedule-base64=<base64>]`), Windows runs its PowerShell twin [`scripts/setup-warmup-repo.ps1`](../../scripts/setup-warmup-repo.ps1) (`&([scriptblock]::Create((irm <raw-url>))) <owner>/<repo> <primetime-web-url> [provider...] [--schedule-base64=<base64>]` — `[scriptblock]::Create` + `&` gives true positional-argument binding without touching disk, unlike `irm | iex`), with the trailing provider ids defaulting to `codex` alone when omitted. `--schedule-base64` is `Buffer.from(JSON.stringify(scheduleConfig)).toString("base64")` — the exact bytes GitHub's Contents API wants, so both scripts pass it straight through as a file's `content` with no local decode/re-encode step — and is what lets each scheduled workflow's due-check step (see `templates/github-actions` below) work without ever calling back to `apps/web` at run time. `lib/providers.ts` deliberately does not import `@primetime/providers` — per the package import boundaries below, `apps/web` never runs a provider adapter itself, so this is just a static display list mirroring the CLI's registered provider ids, not a read of the real registry. Both scripts create `<repo>` via `gh repo create` if it doesn't exist yet, then for each selected provider fetch that provider's own workflow template (`codex-prime-hosted.yml` or `claude-code-prime.yml`) from `raw.githubusercontent.com` (so there's one source of truth for those files rather than a duplicate baked into the web app), substitute the placeholder URL, and write it to a provider-specific workflow path, so `apps/web` no longer needs its own copy of any workflow YAML; they then write `--schedule-base64`'s value (if given) to `.primetime/schedule.json` in `<repo>` the same way, or print a warning and skip it if omitted. UI primitives live in `components/ui/` (shadcn-style: `cva`-based `Button`/`Badge`/`Card`/`Input`, plain `Separator`/`Label`) plus `components/code-block.tsx` (copy-to-clipboard), `components/os-command-tabs.tsx` (the per-OS tab switcher, using `lib/detect-os.ts` for client-side OS detection with a macOS/Linux fallback), and `components/nav.tsx` (a sticky, floating rounded-rectangle bar). The app is light-mode only (no dark-mode media query) with a warm-paper palette (`--color-ember` as the single vivid accent, `--color-warning` for error states) defined in `app/globals.css`'s `@theme` tokens; Tailwind v4 is configured via `postcss.config.mjs`, no `tailwind.config.*` needed. The hero heading uses a serif display font (`next/font/google` Fraunces, wired via `lib/fonts.ts`).
- `templates/github-actions` — all three templates below share the same scheduling mechanism: a tight, fixed cron cadence every 15 minutes, all day (`cron: "7,22,37,52 * * * *"`, offset off cron's round marks per GitHub's own delay-risk guidance, rather than `"*/15 * * * *"` — GitHub Actions cron is fixed-UTC and can't itself track an IANA zone's DST shifts or, once dead-time windows exist, more than one trigger time per day, so none of them try to compute a single precise cron line), a new first-ish step that checks out the repo the workflow itself lives in (distinct from the existing "Check out PrimeTime" step, which checks out PrimeTime's own source into `primetime/` to build the CLI) so `.primetime/schedule.json` is on disk, then a "Read last-primed state" step reading that provider's own `.primetime/state-<provider>.json` (if present) for a `lastPrimedAt` timestamp, then a "Check whether a primer is due" step running `primetime schedule due .primetime/schedule.json <provider> --tolerance-minutes 20 [--last-primed-at <timestamp>]` (the provider id is a literal, statically known per template) and translating its exit code (`0`/`2`/other) into a `due=true`/`due=false`/job-failure `$GITHUB_OUTPUT`, and every remaining step gated on `steps.due-check.outputs.due == 'true'`. A missing `.primetime/schedule.json` fails the job loudly (exit `1`) rather than guessing "always due" or "never due" — see `templates/github-actions/README.md`'s "Scheduling" section for the full rationale. On a successful primer, a final "Persist primer state" step commits that provider's `.primetime/state-<provider>.json` (just a timestamp, never a credential) back to the repo with the default `GITHUB_TOKEN` (`permissions.contents: write` in all three templates for exactly this), feeding the next run's catch-up check — each provider's own state file keeps the two providers' due-checks from interfering with each other. `codex-prime.yml`, the scheduled workflow: restores `auth.json` from the `CODEX_AUTH_JSON` secret, runs `prime codex`, then (using `PRIMETIME_SECRETS_PAT` as `GH_TOKEN`) persists whatever Codex refreshed by running `setup codex` again from inside the runner — reusing the CLI rather than reimplementing the write-back in YAML. Uses only user-controlled secrets, never embeds credentials, and is meant to be copied into a user's own repo (see its header comment). See the README's "GitHub Actions credential setup" section for the `auth.json` refresh/write-back constraints this depends on, sourced from OpenAI's own CI/CD auth docs — don't change this workflow from assumptions without re-reading that section. `codex-prime-hosted.yml` is the same workflow with the write-back step replaced by a GitHub Actions OIDC exchange against `apps/web`'s `/api/actions/token` (see the README's "Hosted setup (GitHub App)" section) instead of `PRIMETIME_SECRETS_PAT` — additive, not a replacement; `codex-prime.yml` stays as the zero-backend self-host path. `claude-code-prime.yml` is the Claude Code equivalent of `codex-prime.yml`: it sets `CLAUDE_CODE_OAUTH_TOKEN` from that secret and runs `prime claude-code`, with no restore-to-file step (it's an env var, not a file) and — unlike Codex — no write-back step or second secret at all, since `claude setup-token`'s token is never refreshed in place the way Codex's `auth.json` is; there is deliberately no `claude-code-prime-hosted.yml`, since that variant would only exist to offer a second way to do a write-back this workflow doesn't need.
- `scripts/setup-warmup-repo.sh` — the plain, reviewable shell script the dashboard's "Create my warmup repository" flow hands macOS/Linux users a one-line `curl | bash` command for. It's not published as any kind of package: it's fetched straight from `raw.githubusercontent.com` at run time, so `main` is always what users run. It takes `<owner>/<repo> <primetime-web-url> [provider...] [--schedule-base64=<base64>]` (trailing provider ids default to `codex` alone when omitted — the dashboard always passes the user's picked provider(s) explicitly; `--schedule-base64` is scanned out of the trailing args before what's left is treated as provider ids), and for each selected provider — dispatched through small `case`-statement helpers (`provider_label`/`provider_cli_binary`/`provider_template_url`/`provider_workflow_path`/`setup_provider`; kept as `case`, not associative arrays, for macOS's stock bash 3.2) — checks that provider's CLI is on `PATH`, clones and builds this repo into a throwaway temp dir (same "not published yet" constraint as everywhere else), shells out to `gh`/that provider's CLI directly for login and the secret write-back (never touching PrimeTime's backend: `codex` via `codex login`/`setup codex` reading a local file, `claude-code` via capturing `claude setup-token`'s printed token and piping it into `setup claude-code` over stdin), and fetches+patches that provider's own workflow template (`codex-prime-hosted.yml` or `claude-code-prime.yml`) to a provider-specific workflow path rather than embedding a copy of it. If `--schedule-base64` was given, it's then written to `.primetime/schedule.json` in `<repo>` via the same `gh api --method PUT contents/...` create-or-update-via-`sha` mechanism used for the workflow files — passed straight through as that file's `content` with no local decode step, since it's already base64 of the exact bytes wanted; if omitted, the script prints a warning that the scheduled workflow's due-check step will fail until one is added. `scripts/setup-warmup-repo.ps1` is its Windows PowerShell twin, given to users through the same dashboard flow via an `irm`-based one-liner (see above) — same steps, same behavior, ported idiom-for-idiom (e.g. explicit `$LASTEXITCODE` checks after every native call, since `$ErrorActionPreference = "Stop"` alone doesn't catch a failing exit code the way bash's `set -e` does; `switch` statements in place of `case`; `-ValueFromRemainingArguments` for the trailing provider/flag list). Keep the two scripts' behavior in sync with each other and with the CLI/templates they wrap rather than reimplementing that logic elsewhere.

Package import boundaries: `apps/cli` depends on `@primetime/github`, `@primetime/providers`, `@primetime/scheduler`, and `@primetime/shared`; `@primetime/providers` depends on `@primetime/github` and `@primetime/shared`; `@primetime/github`, `@primetime/github-app`, and `@primetime/scheduler` each depend on `@primetime/shared`; `apps/web` depends on `@primetime/github-app`, `@primetime/scheduler`, and `@primetime/shared` (resolved as ordinary workspace packages through their built `dist/` output, exactly like `apps/cli` consumes `@primetime/providers`) — never `@primetime/providers` itself, since `apps/web` never runs a provider adapter (see `lib/providers.ts` above). Keep provider-specific logic out of `shared` and out of the CLI layer — new provider behavior belongs in its own subdirectory under `packages/providers/src/`.

## Working conventions specific to this repo

- Every provider operation that isn't implemented yet must throw a clear "not implemented" error (see `ProviderOperationNotImplementedError`) rather than silently no-op or fake success — this is load-bearing for the "never touches credentials" guarantee.
- Never log, echo, or include authentication material (or user-supplied values that might look like secrets) in error messages or output.
- When adding a new provider, isolate it behind the `ProviderAdapter` interface; do not assume auth, CLI behavior, or credential storage matches other providers.
- Don't assume tests/build/lint passed — actually run `npm run typecheck` / `npm test` and report real results.
